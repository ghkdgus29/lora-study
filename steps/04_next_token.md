# 4단계: LLM은 "다음 토큰 분류기"다

**목표**: 토크나이저 · `model(...).logits` · greedy 생성 · "위치 t-1이 토큰 t를 예측한다"를 작은 모델(Qwen3-0.6B)로 직접 본다.
이 네 가지를 알면 학습 쪽의 `encode()`와 `answer_loss()`(5, 6단계), 평가 쪽의 점수 매기기(8단계)가 전부 읽힌다.

## 핵심 개념

### 토크나이저
글자를 정수 id로 바꾼다. 모델은 정수만 본다. 한국어는 글자 단위로 잘게 쪼개지는 경우가 많다(`'재', '고', ' 수', '량'`).

**토큰은 "글자"가 아니라 "어휘 사전의 한 항목"이다.** 토크나이저는 사전(어휘, vocabulary)을 하나 들고 있고, 문자열을 사전에 있는 조각들로 쪼갠 뒤 각 조각의 번호(id)를 돌려준다.
사전의 조각은 자주 같이 나오는 글자 묶음이고, **앞 공백도 글자의 일부**로 들어간다. 영어는 단어 앞에 공백이 거의 항상 붙으므로 `' Y'`, `' the'`처럼 공백 붙은 조각이 따로 등록돼 있다.

실제로 Qwen3-0.6B 토크나이저로 `"[1] Y\n[2] N"`을 쪼개면(스크립트 A)
```
조각  '['  '1'  ']'  ' Y'  '\n'  '['  '2'  ']'  ' N'
id    58   16   60   809   198   58   17   60   451
```
`]` 다음은 `' Y'` 한 조각(id 809)이지 `' '` + `'Y'` 두 조각이 아니다. 그리고 공백 없는 `'Y'`는 전혀 다른 번호(id 56)다. 모델이 보기에 809와 56은 "고양이"와 "자동차"만큼 무관한 두 클래스다.

| 문자열 | id (Qwen3-0.6B) | id (Qwen3.6) |
|---|---|---|
| `' Y'` | 809 | 783 |
| `'Y'` | 56 | 56 |
| `' N'` | 451 | - |
| `'N'` | 45 | - |

이것이 코드 두 군데에 영향을 준다.
- **학습**: 답 `[1] Y`의 Y는 항상 `' Y'`(809) 자리에서 나온다. 그래서 가중치(3단계)를 줄 토큰을 `y_id = tok.encode(" Y")`로 잡는다. `"Y"`로 잡으면 id 56을 가리키게 되어 답 토큰 중 어느 것과도 안 맞고 가중치가 아무 데도 안 붙는다.
- **평가**: 모델이 생성한 글자를 읽을 때 `' Y'`든 `'Y'`든 사람 눈에는 Y다. 모델이 어쩌다 공백 없는 쪽을 내도 틀린 답이 아니므로, 평가 코드는 둘 다 Y로 센다.

**어휘 크기와 lm_head.** 3단계의 "클래스 개수"가 어휘 크기다. 다음 토큰 예측이란 이 사전의 항목 중 하나를 고르는 분류이므로, 모델의 마지막 층(lm_head)은 hidden 벡터를 받아 **사전 항목 수만큼의 점수(logits)** 를 낸다. 1단계로 쓰면 `logits = W_head · h`, W_head의 shape는 `[어휘 크기, hidden]`.

| | 토크나이저 사전 항목 수 `len(tok)` | 모델 `config.vocab_size` (= lm_head 출력 수) |
|---|---|---|
| Qwen3-0.6B | 151,669 | 151,936 |
| Qwen3.6-35B | 248,077 | 248,320 |

두 숫자가 조금 다르다. 그림으로 보면 (0.6B 기준)
```
토크나이저 사전:  id 0 ─────────────── id 151,668          (항목 151,669개. 모두 어떤 문자열에 대응)
lm_head 출력 칸:  칸 0 ─────────────── 칸 151,668 │ 칸 151,669 ─── 칸 151,935
                  ← 사전 항목과 1:1로 짝지어진 칸 →   │ ← 여분 267칸. 짝지어진 문자열이 없다 →
```
lm_head의 W_head shape가 `[151,936, 1024]`이므로 위치마다 점수가 151,936개 나오는데, 뒤쪽 267개는 **사전에 그 번호의 글자가 없다**. 모델 설계자가 이렇게 넉넉히 잡은 이유는
1. 나중에 특수 토큰(`<think>` 같은 것)을 추가할 때 사전에 항목만 넣으면 되고 lm_head 행렬을 다시 만들 필요가 없다.
2. GPU 행렬곱은 크기가 64·128의 배수일 때 빠르다. 151,936 = 128 × 1,187 이고 248,320 = 128 × 1,940 이다.

그러면 여분 칸이 분류를 망치지 않나. 사전학습 데이터는 전부 토크나이저를 거쳐 만들어지므로 정답 id가 여분 칸인 적이 한 번도 없다. 3단계 기울기 `p_i − onehot_i`에서 여분 칸은 onehot이 항상 0이라 기울기가 늘 `+p_i`, 즉 **"점수를 내려라"만 수십억 번 받았다**. 그래서 점수가 바닥에 깔려 있다. 실제로 재 보면(0.6B, 프롬프트 `[1] Y\n[2]`의 마지막 위치)

| | logits | softmax 확률 |
|---|---|---|
| 여분 267칸 | −2.25 ~ −0.98 | 합쳐서 0.0000023 |
| 실제 항목 중 최대 (`' Y'`) | 14.5 | 0.147 |

여분 칸에 모인 확률이 100만분의 2라, 분류에서는 없는 것과 같다. 코드에서도 신경 쓸 일이 없다. `F.cross_entropy`는 151,936개 중 하나를 고르는 분류로 계산하고, 정답 id는 항상 사전 범위 안이다.

정리하면 "어휘 크기"라고 부르는 숫자는 문맥에 따라 둘 중 하나다. 토큰을 셀 때(`len(tok)`)는 사전 항목 수, 모델의 logits·lm_head·메모리 계산을 할 때는 `vocab_size`다.
아래 "logits의 모양"의 248,320, 3단계의 "클래스 248,320개", 6단계의 "13,000 × 248,320 × 4바이트"는 전부 후자다.

### logits의 모양 `[배치, 길이, 어휘]`
forward 한 번에 **모든 위치**에서 "다음 토큰"의 점수(어휘 전체)가 나온다. 길이 13,000 × 어휘 248,320 × 4바이트 = 13GB. 한 예시의 logits가 이만큼이라 실전 코드는 답 위치 53개만 계산한다(`logits_to_keep`, 6단계).

**길이(L)란.** 모델에 넣은 **토큰 개수**다. 글자 수나 단어 수가 아니라 토크나이저가 쪼갠 조각의 수. `"[1] Y\n[2] N"`은 9조각이니 L = 9, 스크립트 D의 `[1] Y\n[2] N\n[3] N`은 14. 실전 예시 하나는 프롬프트 약 8,300 + 답 52 ≈ 8,350이고, 긴 것은 13,000이다.
1단계의 열=토큰 표기로는 X `[hidden, L]`의 열 개수가 L이다. 예시마다 다르므로 shape에 숫자 대신 L로 쓴다.

**왜 3차원인가.** 1단계의 `Y = W·X`를 떠올리면 된다. 모델 본체(attention 층들)는 입력 토큰 L개를 각각 hidden 벡터로 바꾼다. 토큰 하나당 벡터 하나이므로 `[L, hidden]`.
lm_head는 이 벡터 하나하나에 `W_head [어휘, hidden]`를 곱해 점수 벡터 `[어휘]`를 만든다. 토큰 L개에 대해 하므로 `[L, 어휘]`.
여기에 예시 여러 개를 한 번에 넣는 배치 차원이 맨 앞에 붙어 `[배치, L, 어휘]`다. 이 공부의 실전 설정은 예시 하나씩이라 배치 = 1.
```
input_ids  [1, L]            정수 id L개
   ↓ 모델 본체
hidden     [1, L, hidden]    위치마다 벡터 하나 (Qwen3.6은 hidden 2,048)
   ↓ lm_head (= 위치마다 W_head · h)
logits     [1, L, 어휘]      위치마다 "다음 토큰" 점수 248,320개
```
`logits[0, t]`는 "위치 t까지 읽고 나서 t+1에 올 토큰"에 대한 점수 벡터다. 스크립트 B는 `logits[0, -1]`(마지막 위치)만 softmax해서 상위 5개를 찍고, D는 모든 위치를 다 쓴다.
여기서 "어휘"는 앞 절의 `vocab_size`(lm_head 출력 칸 수 = 사전 항목 수 + 여분)다.

**손으로 한 번.** 어휘 5개, hidden 2, 토큰 3개(L = 3)로 줄여서 1단계 연습 1(E → W → pred)과 똑같이 따라간다. 배치 차원은 빼고 PyTorch 표기(행 = 토큰)로 쓴다.

```
사전: 0:'[' 1:'1' 2:']' 3:' Y' 4:'\n'      ← 어휘 5개
E (임베딩표) [5, 2] = [[1,0],[0,1],[1,1],[2,0],[0,2]]     ← 사전 항목마다 벡터 하나
W_body [2, 2] = [[1,1],[0,1]]                            ← 모델 본체를 행렬 하나로 흉내
W_head [5, 2] = [[1,0],[0,1],[1,1],[2,0],[0,2]]          ← lm_head. 행 = 어휘 항목
```

① **input_ids `[L]` = [2, 0, 4]** (`']'`, `'['`, `'\n'`). 정수 3개.

② **임베딩 → X `[L, hidden]`**: id마다 E의 그 행을 꺼낸다(1단계 풀이 7의 복사).
```
X = [E[2]; E[0]; E[4]] = [[1,1],
                          [1,0],
                          [0,2]]        ← 토큰 3개, 각각 2차원 벡터
```
③ **모델 본체 → hidden H `[L, hidden]`**: 여기서는 `H = X · W_bodyᵀ`로 흉내 낸다.
```
H = [[1,1],[1,0],[0,2]] · [[1,0],[1,1]] = [[2,1],
                                           [1,0],
                                           [2,2]]        ← 여전히 토큰 3개, 2차원
```
진짜 모델은 이 자리에 attention 층 수십 개가 있고, 위치 t의 h_t가 **자기보다 앞 토큰 전부**를 보고 만들어진다(그래서 h_t가 "t까지 읽은 상태"다). shape는 들어온 그대로 `[L, hidden]`.

④ **lm_head → logits `[L, 어휘]`**: `logits = H · W_headᵀ`. `[3, 2] · [2, 5] = [3, 5]`.
```
logits = [[2,1],[1,0],[2,2]] · [[1,0,1,2,0],
                                 [0,1,1,0,2]]
       = [[2, 1, 3, 4, 2],        ← 위치 0 (']'까지 읽음): 어휘 5개의 점수. 최대 = 3번 ' Y'
          [1, 0, 1, 2, 0],        ← 위치 1 ('['까지 읽음): 최대 = 3번
          [2, 2, 4, 4, 4]]        ← 위치 2 ('\n'까지 읽음): 2, 3, 4번이 동점
```
칸 하나씩 보면. 결과 `[3, 5]`의 (t, v) 칸은 H의 t행과 W_head의 v행의 내적이다(1단계 "결과 행렬의 칸 = 왼쪽 행 · 오른쪽 열"). 위치 0, 즉 h₀ = [2, 1]로 다섯 칸을 전부 쓰면

| 어휘 항목 v | W_head[v] | h₀ · W_head[v] | 뜻 |
|---|---|---|---|
| 0 `'['` | [1, 0] | 2·1 + 1·0 = **2** | "다음이 `[`일 점수" |
| 1 `'1'` | [0, 1] | 2·0 + 1·1 = **1** | "다음이 `1`일 점수" |
| 2 `']'` | [1, 1] | 2·1 + 1·1 = **3** | "다음이 `]`일 점수" |
| 3 `' Y'` | [2, 0] | 2·2 + 1·0 = **4** | "다음이 ` Y`일 점수" |
| 4 `'\n'` | [0, 2] | 2·0 + 1·2 = **2** | "다음이 `\n`일 점수" |

이 다섯 개가 logits의 0행 `[2, 1, 3, 4, 2]`다. 1행은 h₁ = [1, 0]로, 2행은 h₂ = [2, 2]로 같은 계산을 한 것.

읽는 법.
- **행 t = 위치 t**: 입력의 t번째 토큰까지 읽은 뒤 모델이 "다음에 올 토큰"에 매긴 점수 묶음. 0행은 첫 토큰 `']'`까지 읽은 뒤, 1행은 `']', '['`까지 읽은 뒤의 예측이다. (이 장난감 본체는 앞 토큰을 안 보지만 진짜 모델은 본다.)
- **열 v = 어휘 항목 v**: "다음 토큰이 v일 점수". 열 3은 어느 행에서나 ` Y`에 대한 점수다.
- **행 안에서 최대인 열** = 모델이 가장 그럴듯하다고 보는 다음 토큰. 0행은 열 3(점수 4)이 최대이므로 greedy 생성이면 `' Y'`를 붙인다. 2행은 열 2, 3, 4가 4로 동점이라 argmax는 그중 첫 번째(2번)를 고른다.
- 행 하나를 softmax하면 3단계의 확률이 된다. 0행: `[0.08, 0.03, 0.22, 0.59, 0.08]`, 합 1. 정답이 ` Y`(3번)였다면 loss = −log 0.59 = 0.52.

즉 **행 하나 = 분류 문제 하나**이고, 입력이 L토큰이면 분류 문제가 L개 나온다. lm_head는 위치마다 어휘 248,320개와 내적을 전부 하는 셈이다.

실전으로 돌아가면 숫자만 바뀐다: L 8,350, hidden 2,048, 어휘 248,320. 그리고 맨 앞에 배치 차원 1이 붙어 `[1, L, 어휘]`.

**왜 13GB인가.** 실전 예시 하나는 프롬프트 약 8,300토큰 + 답 52토큰이고, 긴 것은 13,000토큰까지 간다. 숫자 개수는
```
13,000 (위치) × 248,320 (어휘) = 3,228,160,000개   ≈ 32억 개
× 4바이트 (fp32)                 = 12.9GB
```
모델 자체는 bf16(2바이트)이지만 cross-entropy는 정밀도 때문에 fp32로 올려 계산하므로(6단계의 `.float()`) 4바이트로 센다. bf16으로 둬도 6.5GB다.
그리고 이것은 forward 한 번 분량이다. backward는 3단계의 `softmax − onehot`을 같은 크기로 또 만들어야 하므로 실제로는 그 두 배 가까이 든다. 35B 모델 가중치만 72GB인 96GB GPU에서는 넣을 자리가 없다.

이 13GB는 **예시 하나를 처리하는 동안만 잠깐 쓰는 메모리**(activation)다. GPU 메모리를 크게 둘로 나누면
| | 크기가 정해지는 기준 | 언제 잡히나 | 예 |
|---|---|---|---|
| 고정: 가중치, optimizer 상태 | 모델 크기 | 학습 시작 때 한 번, 끝까지 유지 | 35B bf16 가중치 72GB, LoRA 파라미터의 Adam m·v(2단계) |
| 가변: activation | **입력 토큰 수 L** (× 배치) | forward 때 생겨서 backward가 끝나면 풀린다 | logits `[L, 어휘]`, 각 층의 hidden `[L, hidden]`, attention 점수 |

logits는 가변 쪽이고, L에 비례해서 커진다. 8,350토큰이면 8.3GB, 13,000토큰이면 12.9GB. 긴 예시 하나가 들어오는 순간만 터지므로 "평소엔 되다가 가끔 OOM"의 원인이 된다.
backward가 끝나면 풀리지만, **다음 예시의 forward 때 또 잡아야** 하므로 가장 긴 예시 기준으로 자리가 있어야 한다. `logits_to_keep`은 이 가변 메모리의 가장 큰 덩어리를 L과 무관한 53행으로 고정시키는 것이다.

**왜 53개만 계산해도 되나.** loss는 답 토큰 52개에서만 잰다(5단계). 프롬프트 위치 8,300개의 logits는 "프롬프트의 다음 토큰을 얼마나 잘 맞혔나"인데, 그것은 학습 목표가 아니므로 구해도 버린다.
위의 `[L, hidden]` → `[L, 어휘]` 곱은 위치마다 독립이라, 필요한 위치만 골라 곱해도 결과가 같다. `logits_to_keep=53`은 "마지막 53개 위치만 lm_head를 통과시켜라"다.
52가 아니라 53인 이유: 답의 첫 토큰을 예측하는 것은 그 **바로 앞 위치**(프롬프트의 마지막 토큰)의 logits이므로, 답 52개를 채점하려면 위치가 한 칸 앞에서부터 53개 필요하다(아래 "teacher forcing"의 한 칸 어긋남). 맨 마지막 위치는 정답이 없어 버린다(`[:-1]`).
작게 그려 보면. 프롬프트 4토큰 + 답 3토큰, L = 7. 위치 번호는 0부터.
```
위치      0    1    2    3  │  4    5    6
토큰      p0   p1   p2   p3 │  a0   a1   a2        ← p = 프롬프트, a = 답
                            │
logits 행 t 는 "위치 t 까지 읽고 t+1 을 예측"
행 3  →  위치 4 (a0) 예측   ← 프롬프트 마지막 토큰 자리에서 답의 첫 토큰을 맞혀야 한다
행 4  →  위치 5 (a1) 예측
행 5  →  위치 6 (a2) 예측
행 6  →  위치 7 예측        ← 위치 7은 없다. 정답이 없으니 채점 불가
```
- 채점에 필요한 행은 3, 4, 5의 **3개(= 답 길이 A)**. 행 0~2는 "프롬프트 다음 토큰 예측"이라 안 쓴다.
- 그런데 필요한 행이 **답 시작보다 한 칸 앞(행 3)에서 시작**한다. 답 토큰 a0을 맞히는 것은 a0 자리가 아니라 그 앞 p3 자리의 logits이기 때문이다.
- `logits_to_keep=k`는 "**마지막 k행**만 계산"이다. k = 3이면 행 4, 5, 6이 남아 행 3이 빠지고 쓸모없는 행 6이 들어온다. 그래서 **k = A + 1 = 4**로 행 3, 4, 5, 6을 받고, 맨 끝 행 6을 `[:-1]`로 버려 3, 4, 5를 쓴다.
- 짝이 되는 정답은 `ids[4:]` = a0, a1, a2. 코드의 `targets = ids[0, p_len:]`이 이것이다(p_len = 4).

실전은 A = 52라 k = 53, 행 53개 중 끝 하나 버리고 52개로 답 52토큰을 채점한다.
```
53 × 248,320 × 4바이트 = 53MB      ← 12.9GB의 1/245
```
hidden `[L, hidden]`은 여전히 L = 13,000 전부 계산한다(attention이 프롬프트 전체를 봐야 하므로). 줄어드는 것은 마지막 lm_head 곱과 그 출력뿐이다. 그래도 어휘 차원이 hidden의 120배라 logits가 메모리의 대부분이었다.

### greedy 생성
"마지막 위치의 확률 최대 토큰을 붙이고 다시 forward"의 반복. `model.generate(do_sample=False)`가 이것이다. 손으로 쓴 루프와 결과가 같다.
서비스 필터도, 평가 스크립트도 greedy다(temperature 0).

### 학습의 시선: teacher forcing
학습할 때는 토큰을 하나씩 생성하지 않는다. **정답 문장을 통째로 넣고 forward 한 번**으로, 위치 t-1의 logits가 토큰 t를 얼마나 잘 맞혔는지(-log P)를 모든 위치에서 동시에 잰다.
- 그래서 "위치 t-1의 logits ↔ 토큰 t"로 **한 칸 어긋나게** 짝을 짓는다. 마지막 위치의 logits는 짝(정답)이 없어 버린다 → `logits[0, :-1]`과 `ids[0, p_len:]`.
- D의 표에서 `[1] Y\n[2] N\n[3] N`을 보면: 처음에는 `[`, `]` 뒤를 못 맞히다가(P 0.000) 두 번째 줄부터 `[`→`2`→`]`를 0.8~1.0으로 맞힌다. 학습 없이 **문맥만으로 패턴을 따라간 것**(in-context learning). 반면 `]` 뒤에 ` Y`냐 ` N`이냐는 0.02~0.34로 모른다 - 이것이 학습으로 가르칠 부분.
