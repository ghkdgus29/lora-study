# 6단계: 답 토큰에만 loss - `answer_loss()` 해부

**목표**: 답 토큰 loss 함수 `answer_loss()` 7줄을 조각내서, 각 줄이 왜 그 모양인지(특히 `logits_to_keep=n_answer + 1`과 `[:-1]`) 숫자로 확인한다. 덤으로 gradient checkpointing이 메모리를 어떻게 줄이는지 본다.

## 핵심 개념

### 한 칸 어긋난 짝 (4단계 D의 복습)
토큰 `P`를 예측하는 것은 위치 `P-1`의 logits다. 답 토큰이 `P .. L-1`(A개)이면 필요한 logits는 위치 `P-1 .. L-2`(A개).
- `logits_to_keep=A+1`: 모델이 **마지막 A+1개 위치**의 logits만 계산한다(위치 `P-1 .. L-1`).
- `[:-1]`: 그중 맨 끝(위치 `L-1`, "`<|im_end|>` 다음"을 예측하는 자리)은 정답이 없으니 버린다 → 위치 `P-1 .. L-2`.
- `targets = ids[0, p_len:]`: 토큰 `P .. L-1`. 길이가 A로 같다.

A에서 전체 logits를 구해 자른 loss(1.5113)와 `logits_to_keep`로 구한 loss가 소수점까지 같다.

### logits_to_keep가 아끼는 메모리
logits는 `[1, L, 어휘]`. L 13,000 × 어휘 248,320 × fp32 4바이트 = **12.9GB**를 예시 하나마다 만들게 된다. 답 위치 53개만 계산하면 53MB. 이것 없이는 96GB GPU에서 35B 모델(72GB)과 긴 예시를 같이 못 돌린다.

### 토큰별 loss를 보면 "무엇을 배우는지"가 보인다 (B)
| 토큰 | 학습 전 P(정답) | 뜻 |
|---|---|---|
| 첫 `[` | 0.000 | 답을 어떻게 시작할지 모른다(`Y`로 시작하려 함). 학습 초반에 금방 배운다 |
| `1`, `]`, 둘째 줄부터의 `[`, 숫자, `]`, `\n` | 0.98~1.00 | 문맥 패턴으로 이미 안다. loss 기여 거의 0 |
| 첫 `\n` | 0.004 | 모델은 `'  \n'`(공백 둘 + 줄바꿈)을 내려 했다 - 맥 확인 때 `MAX_NEW_TOKENS` 64로 10줄이 잘린 원인 |
| ` Y`, ` N` | 0.60 / 0.03 / 0.97 | **판단**. 학습이 실제로 바꾸는 곳. 3번 ` Y`는 1번을 보고 따라 한 것(진짜 판단이 아님) |
| `<|im_end|>` | 1.000 | 끝낼 줄 안다 |

답 52토큰 중 Y/N은 10개뿐이고 나머지는 형식 토큰이라 loss 평균이 빠르게 떨어지는 것은 형식을 배운 것일 수 있다. **loss가 낮아졌다 ≠ Y/N을 잘 고른다** - 그래서 학습이 끝나면 val 데이터로 F1을 따로 잰다(8단계).

### 가중 평균
`(ce * weight).sum() / weight.sum()`: 가중치를 준 토큰이 평균에서 그만큼 여러 번 세어진다. `--y-weight 3`이면 ` Y` 토큰 3개가 9개로 세어지는 셈. 가중치 1이면 보통 평균과 같다(B의 두 값이 같다).

### gradient checkpointing (C)

**왜 forward의 중간 결과를 저장해야 하나.** 학습은 forward(입력 → loss)와 backward(loss → 각 가중치의 기울기) 두 단계다. backward는 연쇄 법칙으로 층을 거꾸로 내려오는데, 어떤 층의 가중치 기울기를 구하려면 **그 층에 forward 때 들어왔던 입력값**이 필요하다. 예를 들어 `y = W·x`에서 `W`의 기울기는 `(loss의 y에 대한 기울기) × x`라서 `x`를 알아야 한다. 그래서 보통은 forward를 하면서 각 층의 입력과 중간값(활성값, activation)을 전부 메모리에 남겨 두고, backward 때 꺼내 쓴다.

숫자 하나짜리 2층 모델로 직접 계산해 본다. 입력 `x = 2`, 가중치 `w1 = 3`, `w2 = 0.5`, 정답 `1`.

Forward (입력 → loss)

| 단계 | 계산 | 결과 |
|---|---|---|
| 1층 | `h = w1·x = 3 × 2` | **h = 6** |
| 2층 | `y = w2·h = 0.5 × 6` | y = 3 |
| loss | `L = (y − 1)² = 2²` | L = 4 |

Backward (loss → 기울기, 거꾸로 내려온다)

| 단계 | 계산 | 필요한 forward 값 |
|---|---|---|
| y의 기울기 | `2 × (y − 1) = 4` | y |
| **w2의 기울기** | `(y의 기울기) × h = 4 × 6 = 24` | **h = 6** |
| h의 기울기 | `(y의 기울기) × w2 = 4 × 0.5 = 2` | - |
| **w1의 기울기** | `(h의 기울기) × x = 2 × 2 = 4` | **x = 2** |

`w2`의 기울기를 구하는 순간 `h = 6`이 필요하다. 이 값은 forward 때 1층이 만들어 2층에 넘긴 중간값이다. 버렸다면 1층을 다시 계산해야 한다. 실제 모델에서는 `h`가 숫자 하나가 아니라 `[길이, 폭]`짜리 텐서이고, 층마다 이런 값이 여러 개 생긴다.

**얼마나 큰가.** 이 활성값은 `층 수 × 시퀀스 길이 × 폭`에 비례하고, attention은 `길이 × 길이`짜리 행렬까지 남긴다. 그래서 가중치보다 훨씬 클 수 있다.

세 인수가 각각 어디서 오는지 보면

- **폭**: 토큰 하나를 나타내는 벡터의 길이(hidden size)다. 0.6B는 1,024. 층 안의 중간값은 토큰마다 이 크기(MLP 안쪽은 그 몇 배)의 벡터 하나다.
- **시퀀스 길이**: 모델은 모든 토큰 위치에 같은 계산을 한다. 그래서 중간값 하나는 벡터가 토큰 수만큼 쌓인 `[길이, 폭]` 텐서다. 프롬프트가 2배 길면 저장할 값도 2배다.
- **층 수**: 모든 층이 자기 중간값을 따로 남긴다. backward는 맨 위층에서 시작해 맨 아래층까지 내려오므로, 아래층의 값은 backward가 거기 도달할 때까지 버릴 수 없다. forward가 끝난 시점에는 전 층의 값이 동시에 메모리에 있다.

**attention의 `길이 × 길이`.** attention은 토큰마다 "다른 토큰 각각을 얼마나 참고할지"를 점수로 계산한다. 토큰 L개가 각각 L개를 보므로 점수표가 `[길이, 길이]`이고, 헤드마다 하나씩 생긴다. 이 표는 폭과 무관하고 길이의 **제곱**으로 커진다. 길이 1,024에서는 약 100만 칸으로 `[길이, 폭]` 텐서 한 장과 같지만, 길이 13,000에서는 1.69억 칸이 된다. 같은 길이의 `[길이, 폭 1,024]` 텐서(1,331만 칸)보다 12.7배 크다. 프롬프트가 길어질수록 이 항이 전체를 지배한다.

**왜 가중치보다 큰가.** 가중치 행렬 한 장은 `[폭, 폭]` 규모이고 입력이 길든 짧든 그대로다. 활성값 한 장은 `[길이, 폭]`이라 길이가 폭보다 길어지면 한 장만으로 가중치 한 장을 넘는다. 장수도 더 많다. 가중치는 한 층에 행렬 몇 개뿐이지만, 활성값은 연산을 하나 지날 때마다 결과가 한 장씩 남고, 덧셈·정규화·활성 함수처럼 가중치가 없는 연산도 여기에 포함된다.

| 상황 | 가중치 | 활성값(저장분) |
|---|---|---|
| 0.6B, 길이 1,024 (C에서 실측) | 1.2GB | **4.56GB** |
| 35B, 길이 13,000 (실전) | 72GB | 수백 GB (추정) |

0.6B(폭 1,024, 28층, bf16 2바이트)로 어림해 보면

- 텐서 한 장: 길이 1,024 × 폭 1,024 ≈ 100만 개 × 2바이트 ≈ **2MB**.
- 층 하나: 이런 텐서를 수십 장 남긴다(attention의 Q/K/V, 폭이 3배인 MLP 중간값, 정규화 전후 값 등). 실측 4.56GB를 28층으로 나누면 층당 약 160MB, 2MB짜리 80장 분량이다.
- 모델 전체: 2MB × 수십 장 × 28층이라 GB 단위가 되고, 가중치 1.2GB를 넘는다.

길이를 13,000으로 늘리면 두 가지가 겹친다.

- 길이에 비례하는 부분: 텐서 한 장이 약 12.7배 커지고, 35B는 폭과 층 수도 더 크다.
- `길이 × 길이`인 attention 행렬: 13,000 × 13,000 ≈ 1.69억 개 × 2바이트 ≈ **338MB**. 이것이 헤드 하나, 층 하나의 분량이라 헤드 수 × 층 수를 곱하면 이것만으로 수백 GB가 된다. 길이가 12.7배 늘 때 이 부분은 약 161배 는다(구현에 따라 이 행렬을 통째로 남기지 않기도 한다).

실전 조합은 96GB GPU에 들어갈 수가 없다. 가중치만으로 72GB를 쓰는데 활성값이 그 몇 배가 된다.

**checkpointing이 하는 일.** 각 층의 **입력만** 남기고(이게 "checkpoint") 층 안쪽의 중간값은 버린다. backward가 그 층에 도달하면 남겨 둔 입력으로 그 층의 forward를 **다시 한 번 계산**해 중간값을 복원하고 바로 쓴 뒤 버린다. 위 예시의 1층과 2층을 실제 모델의 한 층 안쪽 연산들이라고 보면, 층 입력 `x = 2`만 남기고 안쪽 중간값 `h = 6`은 버렸다가, backward 때 `x`와 `w1`로 `h`를 다시 계산하는 것이다. 즉 메모리를 시간과 맞바꾼다.

- 메모리: 4.56GB → **0.08GB** (C 실측). 길이를 2배로 늘려도 켬 쪽은 거의 안 늘어난다(실험 표 참고).
- 시간: 층마다 forward를 한 번 더 하므로 forward+backward가 느려진다. C에서는 1.7배였고, GPU에서는 보통 20~40% 추가 정도다(backward가 forward보다 원래 무거워서 forward 한 번 더 하는 비중이 그만큼이다).

긴 프롬프트(13k 토큰)로 큰 모델(35B)을 학습할 때는 이걸 켜지 않으면 아예 돌지 않으므로 항상 켠다. `gradient_checkpointing_enable(gradient_checkpointing_kwargs={"use_reentrant": False})`의 `use_reentrant=False`는 PyTorch의 새 구현을 쓰라는 뜻이다. 옛 구현(`True`)에는 아래 문제가 있고, 새 구현에는 없다.

**`enable_input_require_grads()`는 무엇을 막는가.** 옛 구현(`use_reentrant=True`)에서 LoRA 어댑터까지 기울기가 도달하지 않는 문제를 막는다. 순서대로 보면

1. **autograd의 규칙.** 연산의 입력 중 하나라도 `requires_grad=True`여야 그 연산이 기록되고, 기록된 연산으로만 기울기가 흐른다.
2. **평소에는 가중치도 입력이다.** `y = W·x`에서 autograd가 보는 입력은 `x`와 `W` 둘이다. LoRA는 임베딩을 포함한 원본 가중치를 전부 고정(`requires_grad=False`)하므로 첫 층에 들어가는 `x`(임베딩 출력)는 False다. 그래도 어댑터 가중치가 True라 연산이 기록된다. checkpointing이 없으면 문제가 없다.
3. **옛 checkpointing은 층을 상자로 감싼다.** 층 안쪽은 기록을 끈 채 계산하고(그래서 중간값이 안 남는다), autograd에는 층 전체를 연산 하나로 등록한다. 이 상자의 입력으로 보이는 것은 상자에 넘긴 텐서, 즉 **층 입력뿐**이다. 어댑터 가중치는 상자 안에 있어 보이지 않는다.
4. **연쇄적으로 끊긴다.** 1층 상자는 입력이 False라 기록되지 않고, 그 출력도 False가 된다. 그것이 2층 상자의 입력이므로 2층도 기록되지 않는다. 마지막 층까지 전부 끊겨 어댑터는 기울기를 받지 못한다.

| | autograd가 보는 입력 | 기록 여부 |
|---|---|---|
| checkpointing 없음 | 층 입력(False), 어댑터 가중치(True) | 기록됨 |
| 옛 checkpointing | 층 입력(False)만 | **기록 안 됨** |

`enable_input_require_grads()`는 임베딩 출력 텐서에 `requires_grad=True`를 강제로 켠다(임베딩 가중치를 학습하는 게 아니라, 그 **출력** 텐서에만 표시를 붙이는 것이다). 그러면 1층 상자의 입력이 True가 되어 상자가 기록되고, backward가 상자에 도달하면 층을 다시 계산하면서 안쪽 어댑터에 기울기를 준다.

**새 구현에서는 이 문제가 없다.** 새 구현(`use_reentrant=False`)은 층 안쪽 연산을 평소처럼 기록하고 중간값만 저장하지 않는다. 어댑터 가중치가 autograd에 그대로 보이므로 층 입력이 False여도 기울기가 흐른다. 고정 임베딩 → 학습 가능한 층 2개 → 고정 head로 된 작은 모델에서 돌려 본 결과(torch 2.15)

| 구현 | 층 입력 | 결과 |
|---|---|---|
| checkpointing 없음 | False | 기울기 정상 |
| 옛 구현 | False | 경고 뒤 `loss.backward()`에서 **에러** |
| 옛 구현 | True | 기울기 정상 |
| 새 구현 | False | **기울기 정상** |

옛 구현은 `None of the inputs have requires_grad=True. Gradients will be None` 경고를 내고, loss까지 기록된 연산이 하나도 없어 `element 0 of tensors does not require grad` 에러로 멈춘다. 에러 없이 넘어가는 경우도 있다. 상자 밖에 학습 가능한 가중치가 따로 있으면 backward는 돌고, 층 안쪽 가중치의 기울기만 `None`으로 남는다. 경고만 나오고 학습은 진행되므로 놓치기 쉽다.

**그러면 왜 부르나.**

- 8·9단계(실전): `use_reentrant=False`라 없어도 기울기는 흐른다. 부르는 비용이 없고, 누가 옛 구현으로 바꿔도 깨지지 않게 하는 안전장치로 둔다. PEFT도 checkpointing이 켜진 모델에 LoRA를 붙일 때 같은 호출을 내부적으로 한다.
- 이 스크립트(C): 모델을 고정하지 않아 임베딩을 포함한 모든 가중치가 True이고, 임베딩 출력도 이미 True다. 그래서 이 호출은 측정 결과를 바꾸지 않는다. 실전 코드와 같은 모양으로 보여 주려고 둔 것이다.

## 실전 코드에서는
```python
def answer_loss(model, ids, p_len, y_id, y_weight):
    n_answer = ids.shape[1] - p_len
    out = model(input_ids=ids, logits_to_keep=n_answer + 1, use_cache=False)   # A
    logits = out.logits[0, :-1].float()                                        # A: 마지막 하나 버림, fp32로
    targets = ids[0, p_len:]                                                   # A
    ce = F.cross_entropy(logits, targets, reduction="none")                    # B (3단계)
    weight = torch.where(targets == y_id, y_weight, 1.0)                       # B
    return (ce * weight).sum() / weight.sum()                                  # B
```
`.float()`: bf16 logits로 softmax를 하면 정밀도가 모자라 loss가 흔들리므로 fp32로 올려 계산한다(53 × 248k × 4바이트 = 53MB라 부담 없다).
