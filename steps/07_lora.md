# 7단계: LoRA - 큰 가중치는 얼리고 작은 보정 행렬만 학습한다

**목표**: `LoraConfig`, `get_peft_model`, `print_trainable_parameters`, `save_pretrained`가 무엇을 하는지, 그리고 `r`, `alpha`, `target_modules`가 무엇을 바꾸는지 안다.

## 핵심 개념

### 왜 전체를 학습하지 않나
파라미터 하나를 Adam으로 학습하려면 가중치 외에 **기울기 + Adam 상태 2개 = 파라미터당 12바이트(fp32)**가 더 든다. 35B면 420GB. 96GB GPU 한 장에는 가중치(72GB)만 겨우 들어간다.
또 데이터가 2,950문항뿐이라 350억 개를 전부 움직이면 금방 과적합한다.

### LoRA(Low-Rank Adaptation)
선형층 `y = W x`에 보정을 더한다: `y = W x + B (A x) * (alpha / r)`.
- `W` (예: 2048×1024)는 **얼린다**(requires_grad=False). 학습하지 않고 메모리에 읽기만.
- `A` (r×1024), `B` (2048×r)만 학습. `r`이 16이면 파라미터 수가 W의 2~3%.
- **`B`는 0으로 시작** → 학습 전에는 보정이 0이라 원래 모델과 출력이 완전히 같다(스크립트 A 파트가 출력하는 `allclose True`). 거기서 조금씩 벗어난다. `A`는 작은 난수로 시작한다. A까지 0이면 A와 B의 기울기가 둘 다 0이 되어 학습이 시작되지 않는다.
- 학습 결과물 = A, B들만 모은 **어댑터**(40MB; 35B에서는 수백 MB). 서비스는 원래 가중치 + 어댑터를 같이 읽는다.

**`A`가 난수인데 왜 출력이 "완전히" 같은가.** 보정은 `A`와 `B`를 **곱한** 것이라, 둘 중 하나만 0이어도 결과가 0이다. `A x`는 0이 아닌 숫자 r개지만(스크립트 A 파트에서는 최대 0.6 정도), 여기에 전부 0인 `B`를 곱하면 무엇이든 0이 된다.

```
A x          = [0.31, −0.12, ...]      (난수 A 때문에 0이 아니다)
B (A x)      = [0, 0, ..., 0]          (0을 곱했으므로 정확히 0. 0에 가까운 값이 아니다)
W x + 0      = W x                     (0을 더했으므로 한 비트도 달라지지 않는다)
```

그래서 근사적으로 같은 것이 아니라 정확히 같다. 스크립트가 쓰는 `torch.allclose`는 "아주 작은 오차 안에서 같은가"를 보는 근사 비교 함수(기본 허용 오차: 상대 1e-5, 절대 1e-8)이지만, 이 경우에는 한 비트까지 같은지 보는 `torch.equal`로 바꿔도 True가 나온다. `allclose`를 쓴 것은 실수 계산을 비교할 때의 습관이다. 같은 값을 다른 순서로 계산하면 반올림 때문에 끝자리가 달라지는 경우가 있어서다. 예를 들어 학습 뒤에 "`W x + B (A x)·s`로 따로 계산한 출력"과 "`W + s·B·A`로 merge한 뒤 계산한 출력"을 비교하면, 수학적으로는 같지만 약 1e-6만큼 달라서 `torch.equal`은 False, `allclose`(허용 오차 1e-6)는 True가 나온다.

**이름의 뜻.** Adaptation은 사전학습 모델을 새 작업에 맞추는 것, 즉 파인튜닝이다. Low-Rank는 그때 가중치에 더하는 변화량을 **랭크가 낮은 행렬**로 제한한다는 뜻이다.

**왜 이것이 파인튜닝이 되나.** 파인튜닝은 가중치를 `W → W + ΔW`로 바꾸는 일이다. 전체 파인튜닝은 `ΔW`의 모든 칸을 자유롭게 정한다(2048×1024면 약 210만 칸). LoRA는 `ΔW`를 `B·A` 꼴로만 허용한다. `B`(2048×r)와 `A`(r×1024)를 곱하면 2048×1024 행렬, 즉 `W`와 같은 크기가 된다. 위 식을 묶으면

```
W x + B (A x) · s  =  (W + s · B A) x        (s = alpha / r)
```

`W`는 건드리지 않았지만 출력은 가중치를 `W + s·BA`로 고친 모델과 똑같다. 그래서 학습이 끝난 뒤 `BA`를 `W`에 더해 하나로 합칠 수도 있다(merge).

**랭크란.** 행렬 안에 서로 독립인 방향이 몇 개 있는가를 세는 수다. 작은 예로 `B`가 3×1, `A`가 1×3이면

```
B = [1]      A = [1 0 2]      B·A = [1 0 2]
    [2]                             [2 0 4]
    [3]                             [3 0 6]
```

`B·A`는 9칸이지만 모든 줄이 `[1 0 2]`의 배수다. 독립인 방향이 하나뿐이라 랭크 1이고, 숫자 6개(A 3개 + B 3개)로 9칸이 전부 정해진다. `B (A x)` 순서로 읽으면 하는 일이 보인다.

입력 `x = [3, 5, 1]`을 넣어 두 단계로 계산해 본다.

**1단계: `A x` - 입력 세 개를 숫자 하나로 줄인다.**

```
A x = [1 0 2] · [3, 5, 1] = 1×3 + 0×5 + 2×1 = 5
```

`A`의 숫자들은 "입력의 각 칸을 얼마나 반영할지"다. 첫 칸은 1배, 둘째 칸은 0배(무시), 셋째 칸은 2배로 더한다. 입력이 세 개였는데 결과는 `5` 하나다. 이것이 "숫자 하나를 읽어 낸다"는 뜻이다. `A`가 재는 것은 "첫 칸과 셋째 칸이 얼마나 큰가"라는 한 가지 성질이고, 5는 그 측정값이다.

"반영한다"는 **곱해서 더한다**는 뜻이고, `A`의 숫자는 각 칸에 곱하는 **비중**이다. 성적 계산과 같은 구조다. 입력이 `[중간 80, 기말 90, 과제 100]`이고 `A = [0.3, 0.5, 0.2]`면 `0.3×80 + 0.5×90 + 0.2×100 = 89`. 점수 세 개가 숫자 하나로 줄었고, 0.3·0.5·0.2가 각 점수의 반영 비중이다. 같은 입력에 `A`만 바꾸면 재는 것이 달라진다.

| `A` | 결과 | 이 숫자가 뜻하는 것 |
|---|---|---|
| `[0.3, 0.5, 0.2]` | 89 | 종합 성적 |
| `[0, 1, 0]` | 90 | 기말 점수만 |
| `[1, −1, 0]` | −10 | 중간이 기말보다 얼마나 높은가 |
| `[0, 0, 0]` | 0 | 아무것도 보지 않음 |

- 비중이 0이면 그 칸은 값이 무엇이든 결과에 영향을 주지 않는다. 위 `A = [1 0 2]`에서 둘째 칸이 무시되는 것이 이 경우다.
- 비중이 크면 그 칸이 조금만 달라져도 결과가 크게 달라진다.
- 비중이 음수면 그 칸이 클수록 결과가 작아진다.

그래서 `A`의 한 줄은 "입력에서 어떤 성질을 잴지"를 정하는 채점 기준이고, `A x`는 그 기준으로 매긴 점수다. 실제 모델에서는 입력이 토큰 하나를 나타내는 숫자 1,024개이고 `A`의 한 줄도 1,024개다. 어떤 비중을 쓸지는 사람이 정하지 않고 학습이 정한다.

**2단계: `B`를 곱한다 - 그 숫자 하나를 출력 세 칸으로 펼친다.**

```
B × 5 = [1, 2, 3] × 5 = [5, 10, 15]
```

`B`의 숫자는 "점수 1당 그 출력 칸을 얼마나 바꿀지"다.

| 출력 칸 | `B`의 값 (점수 1당 변화량) | 점수 5일 때 보정값 |
|---|---|---|
| 첫째 | 1 | 5 |
| 둘째 | 2 | 10 |
| 셋째 | 3 | 15 |

`B`가 달라지면 같은 점수로도 출력이 다르게 바뀐다. `B = [1, 0, −2]`면 보정값은 `[5, 0, −10]`이다. 첫째 칸은 올리고, 둘째 칸은 그대로 두고, 셋째 칸은 내린다.

"펼친다"고 한 이유는 칸 수 때문이다. 보정값은 원래 출력에 더해야 하므로 출력과 칸 수가 같아야 하는데, 1단계 결과는 숫자 하나뿐이다. 그래서 그 하나를 출력 칸 수만큼의 숫자로 늘린다. 실제 모델에서는 숫자 r개를 2,048개로 늘린다.

이 `[5, 10, 15]`가 보정값이고, 원래 출력 `W x`에 더해진다. `B·A`를 먼저 곱해 놓고 계산해도 같은 값이 나온다(`[1 0 2]·x = 5`, `[2 0 4]·x = 10`, `[3 0 6]·x = 15`).

**입력을 바꿔 보면 "한 방향"의 뜻이 보인다.**

| 입력 `x` | 1단계 `A x` | 2단계 보정값 |
|---|---|---|
| `[3, 5, 1]` | 5 | `[5, 10, 15]` |
| `[1, 0, 0]` | 1 | `[1, 2, 3]` |
| `[0, 9, 0]` | 0 | `[0, 0, 0]` |
| `[−2, 0, 0]` | −2 | `[−2, −4, −6]` |

보정값은 어떤 입력에서도 `[1, 2, 3]`에 숫자 하나를 곱한 꼴이다. 세 칸의 비율 1:2:3은 고정이고, 입력에 따라 달라지는 것은 **얼마나 세게, 어느 쪽으로**(양수/음수)뿐이다. 이것이 "출력을 `[1 2 3]` 방향으로 민다"는 뜻이다. `[1, 0, 0]`이나 `[0, 1, −1]` 같은 다른 비율의 보정은 이 `B`로는 만들 수 없다.

정리하면 `A`는 **무엇을 볼지**(입력에서 어떤 성질을 잴지)를 정하고, `B`는 **어떻게 바꿀지**(출력을 어떤 비율로 움직일지)를 정한다. `A`가 조건을 재고 `B`가 행동을 정하는 셈이다. 점수가 0이면 보정값도 전부 0이라 출력이 그대로이고, 점수가 클수록 출력이 많이 바뀐다. 랭크 1 보정은 "입력에서 성질 하나를 재고, 그 값만큼 출력을 한 방향으로 미는" 규칙 하나다. 학습은 이 `A`와 `B`의 숫자들을 정하는 일이다.

`q_proj`에 붙인 LoRA로 예를 들면 출력은 토큰의 질문 벡터다. 이때 규칙은 "입력 토큰에 어떤 성질이 강하면, 그 토큰이 찾는 정보를 이렇게 바꿔라"가 된다.

**r이 커지면 규칙이 늘어난다.** `r = 2`면 `A`가 두 줄이라 숫자 두 개를 읽어 내고, `B`가 두 열이라 방향도 두 개다.

```
A = [1 0 2]      B = [1 0]      x = [3, 5, 1]
    [0 1 0]          [2 0]
                     [3 1]

A x = [5, 5]                                       (성질 두 개를 잰다)
보정 = 5 × [1, 2, 3] + 5 × [0, 0, 1] = [5, 10, 20]   (두 방향으로 민 것을 더한다)
```

규칙마다 보정값이 따로 나오고, 출력은 하나뿐이므로 칸마다 더해 최종 보정값 하나로 만든다.

| 규칙 | 1단계 점수 | 2단계 보정값 |
|---|---|---|
| 첫째 | 5 | `5 × [1, 2, 3] = [5, 10, 15]` |
| 둘째 | 5 | `5 × [0, 0, 1] = [0, 0, 5]` |
| 합 | | `[5, 10, 20]` |

`r = 16`이면 이런 규칙이 16개이고, 보정값은 16개 방향을 섞어서 만들 수 있는 범위 안에서 정해진다.

**보정이 기존 가중치에 주는 영향.** 위 `r = 2` 예에 원래 가중치 `W`를 붙여 끝까지 계산해 본다.

```
W = [2 0 1]       W x = [7, 5, 8]      (원래 모델의 출력)
    [0 1 0]
    [1 1 0]

y = W x + 보정 = [7, 5, 8] + [5, 10, 20] = [12, 15, 28]      (LoRA를 붙인 층의 출력)
```

`W`는 계산에 그대로 쓰였을 뿐 한 칸도 바뀌지 않았다. 그런데 `B·A`를 미리 곱해 `W`에 더한 행렬로 계산해도 같은 출력이 나온다.

```
B·A = [1 0 2]       W + B·A = [3 0 3]       (W + B·A) x = [12, 15, 28]
      [2 0 4]                 [2 1 4]
      [3 1 6]                 [4 2 6]
```

그래서 LoRA의 영향은 두 가지로 말할 수 있다.

- 저장된 값으로 보면: `W`는 그대로이고, `A`와 `B`가 옆에 따로 있다.
- 모델의 동작으로 보면: 가중치가 `W`에서 `W + B·A`로 바뀐 모델과 똑같이 움직인다. 위 예에서는 9칸 중 8칸이 달라졌다.

`B·A`의 각 칸은 "입력의 그 칸이 출력의 그 칸에 주는 영향을 얼마나 바꿀지"다. `W`의 첫 줄 첫 칸은 2였는데 3이 됐으므로, 입력 첫 칸이 출력 첫 칸에 주는 영향이 2배에서 3배로 커졌다. 실제로는 보정값에 배율 `alpha / r`이 곱해지므로 바뀐 가중치는 `W + (alpha / r)·B·A`이고, 학습이 끝난 뒤 이 값을 `W`에 실제로 더해 버리는 것이 앞에서 말한 merge다.

**왜 낮은 랭크로 충분한가.** 사전학습 모델은 이미 언어와 지식을 갖고 있으므로, 새 작업에 맞추는 데 필요한 변화는 소수의 방향을 조정하는 것으로 표현된다는 가설이다. LoRA 논문이 이 가설에서 출발했고, r이 한 자릿수여도 전체 파인튜닝에 가까운 결과를 보고했다. 증명된 사실이 아니라 실험으로 뒷받침된 가설이라, 작업이 사전학습과 많이 다를수록 더 큰 r이 필요할 수 있다.

**코드에서 `x`의 모양과 `.T`.** 스크립트 A 파트의 `LoRALinear.forward`는 식 `W x + B (A x) · s`를 이렇게 쓴다.

```python
return self.base(x) + (x @ self.A.T @ self.B.T) * self.scale
```

`x`의 모양은 `(..., 입력 크기)`다. 마지막 차원만 입력 크기와 같으면 되고, 앞쪽 차원은 몇 개든 상관없다.

| 어디서 | `x`의 모양 | 뜻 |
|---|---|---|
| 스크립트 A 파트 | `(4, 256)` | 256칸짜리 벡터 4개 |
| 실제 모델의 `q_proj` | `(배치, 토큰 수, 1024)` | 문장 1개에 토큰 5개면 `(1, 5, 1024)`. 토큰마다 1,024칸 |

수식의 `x`는 세로로 세운 벡터 **하나**다. 코드의 `x`는 벡터 여러 개를 **가로줄로 쌓은 것**이다. `(4, 256)`이면 한 줄이 벡터 하나다. 줄마다 `A`를 적용하려면 `A`를 오른쪽에서 곱해야 하고, 그러려면 `A`를 뒤집어야(전치) 모양이 맞는다.

```
x          (4, 256)
@ A.T      (256, 16)    →  (4, 16)      줄마다 A x  (256칸을 r=16칸으로 줄임)
@ B.T      (16, 256)    →  (4, 256)     줄마다 B (A x)  (16칸을 출력 크기로 펼침)
```

`@`는 맞닿는 두 차원이 같아야 한다. `A`는 `(16, 256)`이라 `x @ A`는 `256`과 `16`이 맞닿아 계산이 안 된다. 수식으로는 `B A x`를 통째로 눕힌 것이다: `(B A x)ᵀ = xᵀ Aᵀ Bᵀ`. 눕히면 곱하는 순서가 뒤집히고 각 행렬에 `ᵀ`가 붙는다. 3차원 입력이어도 `@`는 마지막 차원에만 작용하므로 `(1, 5, 1024) → (1, 5, 16) → (1, 5, 2048)`로 토큰마다 같은 계산이 된다.

**`A`, `B`를 처음부터 반대 모양으로 만들면 `.T`가 필요 없지 않나.** 맞다. `A`를 `(입력, r)`, `B`를 `(r, 출력)`으로 만들면 `x @ A @ B`로 쓸 수 있고, 계산 결과와 학습 결과는 완전히 같다. 숫자를 어느 방향으로 저장하느냐의 차이일 뿐이다. 그런데도 `(r, 입력)`, `(출력, r)`로 만드는 것은 관례를 따르기 위해서다. 이유 네 가지를 하나씩 본다.

**1. nn.Linear가 `W`를 `(출력, 입력)`으로 저장한다.** 수식 `y = W x`에서 `W`의 한 줄은 "출력 한 칸을 만들 때 입력 각 칸에 곱하는 비중"이다. 출력이 2칸, 입력이 3칸이면 2줄 × 3칸, 즉 `(출력, 입력)` 모양이다. nn.Linear는 이 수식의 모양 그대로 저장한다.

```python
lin = nn.Linear(3, 2)      # 입력 3 -> 출력 2
lin.weight.shape           # (2, 3)  <- (출력, 입력). 만들 때 쓴 순서 (3, 2)와 반대다
```

한편 데이터는 가로줄로 쌓여 있으므로(`x`가 `(벡터 개수, 3)`), nn.Linear는 안에서 `x @ W.T`를 계산한다. 위 `r = 2` 예의 `A`를 `W` 자리에 넣어 보면

```
W = [1 0 2]      x = [3 5 1]      x @ W.T = [5 5]      첫 줄은 앞에서 손으로 계산한 A x = [5, 5]
    [0 1 0]          [1 0 0]                [1 0]
```

그래서 `forward`의 `self.base(x)`도 안에서는 `x @ W.T`(+ bias)다. 식 전체를 풀어 쓰면 세 행렬이 같은 방식으로 쓰인다.

```
self.base(x)  +  (x @ self.A.T @ self.B.T) * self.scale
=  x @ W.T    +   x @ A.T @ B.T · s
```

`W`, `A`, `B` 모두 `(나가는 크기, 들어오는 크기)`로 저장하고 `.T`로 곱한다. `A`는 "입력 → r인 nn.Linear의 `W`", `B`는 "r → 출력인 nn.Linear의 `W`"와 같은 모양이다. 실제로 `A`, `B`를 nn.Linear로 만들면 `.T`가 코드에서 보이지 않게 된다.

```python
self.A = nn.Linear(base.in_features, r, bias=False)    # weight 모양 (r, 입력)
self.B = nn.Linear(r, base.out_features, bias=False)   # weight 모양 (출력, r)
...
return self.base(x) + self.B(self.A(x)) * self.scale   # .T는 nn.Linear 안에서 일어난다
```

`.T`가 없어진 것이 아니라 nn.Linear 안으로 들어간 것이다. PEFT가 이 방식으로 만든다(3번).

**2. `B @ A`가 `W`와 같은 모양이라 merge가 식 그대로다.** merge는 `W`에 `s·B·A`를 칸끼리 더하는 일이라 두 행렬의 모양이 같아야 한다. `q_proj`(1024 → 2048, r 16)로 보면

```
지금 모양:   B (2048, 16) @ A (16, 1024)  =  (2048, 1024)    W (2048, 1024)와 같다
반대 모양:   A (1024, 16) @ B (16, 2048)  =  (1024, 2048)    W와 가로세로가 반대다
```

반대 모양으로 만들면 forward에서는 `.T`가 사라지지만 merge에서 뒤집어야 한다.

| | forward | merge |
|---|---|---|
| 지금 모양 | `x @ A.T @ B.T` | `W + s * (B @ A)` |
| 반대 모양 | `x @ A @ B` | `W + s * (A @ B).T` |

즉 `.T`는 없앨 수 없고 자리만 옮길 수 있다. `W`는 `(출력, 입력)`으로 저장되어 있고 데이터는 가로줄로 쌓여 있어서, 둘이 만나는 곳 어딘가에서 한 번은 뒤집어야 하기 때문이다. `W`의 모양은 nn.Linear가 정한 것이라 바꿀 수 없다. 그러니 `A`, `B`를 `W`와 같은 방식으로 두는 쪽이 앞에서 쓴 식 `W + s·B·A`와 코드가 그대로 맞아 읽기 쉽다.

**3. PEFT의 `lora_A`, `lora_B`와 모양이 같다.** PEFT는 1번 끝에서 본 방식대로 `lora_A = nn.Linear(입력, r, bias=False)`, `lora_B = nn.Linear(r, 출력, bias=False)`로 만든다. 그래서 가중치 모양이 `(r, 입력)`, `(출력, r)`이다.

| | `A` 쪽 | `B` 쪽 |
|---|---|---|
| 손으로 만든 `LoRALinear` (1024 → 2048, r 16이라면) | `A` `(16, 1024)` | `B` `(2048, 16)` |
| PEFT의 `q_proj` (스크립트 B 파트 출력) | `lora_A` `(16, 1024)` | `lora_B` `(2048, 16)` |

`save_pretrained`가 저장하는 어댑터 파일 안의 값도 이 모양이다. 손으로 만든 것과 PEFT의 것이 같은 자리에 같은 뜻의 숫자를 갖고 있으므로, A 파트에서 이해한 것을 B 파트의 출력이나 어댑터 파일에 그대로 대응시킬 수 있다. 반대 모양으로 만들었다면 PEFT 쪽을 볼 때마다 머릿속에서 뒤집어야 한다.

**4. `.T`는 값을 복사하지 않는다.** 텐서는 두 부분으로 되어 있다. 숫자들이 한 줄로 늘어선 **메모리**와, "이 숫자들을 몇 줄 몇 칸으로 읽을지"를 적은 **읽는 방법**이다. `.T`는 메모리는 그대로 두고 읽는 방법만 바꾼 텐서를 돌려준다(이런 텐서를 view라고 한다).

```
메모리:   1 0 2 0 1 0          (숫자 6개. 하나뿐이다)

A   (2줄 3칸으로 읽기):  [1 0 2]        A.T (3줄 2칸으로 읽기):  [1 0]
                         [0 1 0]                                 [0 1]
                                                                 [2 0]
```

둘이 같은 메모리를 보고 있어서 `A.T[2, 0] = 99`로 고치면 `A`의 첫 줄 셋째 칸도 99가 된다. 여기서 두 가지가 따라 나온다.

- **속도.** `forward`가 불릴 때마다 `.T`를 하지만 `(16, 1024)`짜리 숫자들을 옮겨 적는 일은 없다. 시간이 드는 곳은 `@`(행렬 곱)이고, 이 계산량은 어느 모양으로 저장하든 같다.
- **학습.** `A.T`는 `A`와 같은 숫자들이므로 `loss.backward()`의 기울기는 `self.A`에 `(r, 입력)` 모양으로 쌓인다. optimizer에 넘긴 `lora.A`, `lora.B`가 그대로 학습된다.

### PEFT - LoRA를 실제 모델에 붙여 주는 라이브러리
PEFT는 **Parameter-Efficient Fine-Tuning**(파라미터 효율적 파인튜닝)의 줄임이다. 이 말은 두 가지를 가리킨다.

1. **기법들의 이름.** 모델 전체를 학습하지 않고 파라미터의 작은 일부만 학습하는 파인튜닝 방법을 통틀어 PEFT라고 한다. LoRA가 그중 하나이고 가장 널리 쓰인다. prefix tuning, prompt tuning, IA³ 같은 다른 방법도 여기에 속한다.
2. **라이브러리의 이름.** Hugging Face가 이 기법들을 구현해 둔 파이썬 패키지가 `peft`다. 코드의 `from peft import ...`가 이것이고, 이 문서에서 "PEFT가 ~한다"라고 쓴 것은 전부 이 라이브러리를 뜻한다.

**왜 라이브러리가 필요한가.** 위에서 본 원리는 nn.Linear 하나에 `A`, `B`를 붙이는 것이었고, 스크립트 A 파트의 `LoRALinear`가 그것을 손으로 만든 것이다. 실제 모델에는 붙일 부품이 196개 있고(아래 `target_modules`), 얼리기·저장·불러오기도 해야 한다. PEFT는 이 일을 함수 몇 개로 대신 해 준다.

| 할 일 | 손으로 하면 (스크립트 A 파트) | PEFT로 하면 (B, C 파트) |
|---|---|---|
| 설정 정하기 | `r`, `alpha`를 직접 넘긴다 | `LoraConfig(r=..., lora_alpha=..., target_modules=...)` |
| 원래 가중치 얼리기 | `base.weight.requires_grad_(False)` | `get_peft_model`이 모델 전체를 얼린다 |
| `A`, `B` 만들어 붙이기 | 부품마다 `LoRALinear(base, r, alpha)`로 감싼다 | `get_peft_model`이 이름이 맞는 부품을 전부 찾아 감싼다 |
| 학습 파라미터 수 확인 | `numel()`을 직접 더한다 | `model.print_trainable_parameters()` |
| 결과 저장 | `A`, `B`만 골라 직접 저장한다 | `model.save_pretrained(폴더)` |

**함수별로 하는 일.**

- **`LoraConfig`**: 설정값을 담는 객체다. 만들 때는 모델에 아무 일도 일어나지 않는다. 아래에서 설명하는 `r`, alpha(`lora_alpha`), `target_modules`, dropout(`lora_dropout`)이 전부 이 객체의 항목이다.
- **`get_peft_model(model, lora)`**: 실제로 모델을 바꾼다. 모든 파라미터를 얼리고, `target_modules`에 이름이 맞는 nn.Linear를 "원래 `W` + `lora_A` + `lora_B`"를 가진 PEFT의 `Linear`로 바꿔 끼운다. 새로 생긴 `lora_A`, `lora_B`만 `requires_grad=True`다. 그래서 실전 코드가 `requires_grad`인 파라미터만 optimizer에 넘기면 LoRA만 학습된다.
- **`print_trainable_parameters()`**: 학습되는 파라미터 수와 전체 대비 비율을 출력한다(`trainable%: 1.67`).
- **`save_pretrained(폴더)`**: 어댑터만 저장한다. 폴더에는 `A`, `B` 값이 든 `adapter_model.safetensors`와 설정이 든 `adapter_config.json`이 생긴다. 원래 가중치는 저장하지 않으므로, 불러올 때는 원래 모델을 먼저 읽고 그 위에 어댑터를 붙인다(`PeftModel.from_pretrained(원래 모델, 폴더)`).

**`task_type`은 무엇인가.** `LoraConfig`의 항목으로, "이 모델을 어떤 종류의 작업에 쓰는가"를 PEFT에 알려 주는 값이다. `r`, `alpha`, `target_modules`와 달리 LoRA의 계산에는 관여하지 않는다. `A`, `B`가 어디에 몇 개 붙는지, 학습 파라미터가 몇 개인지는 이 값과 무관하다. 이 값이 정하는 것은 `get_peft_model`이 모델을 **어떤 포장 클래스로 감싸서 돌려줄지**다.

| `task_type` | 모델이 하는 일 | 돌려주는 클래스 |
|---|---|---|
| `"CAUSAL_LM"` | 앞 토큰들을 보고 다음 토큰을 예측한다 (GPT, Qwen 등) | `PeftModelForCausalLM` |
| `"SEQ_2_SEQ_LM"` | 입력 문장을 읽고 출력 문장을 만든다 (T5 같은 인코더-디코더) | `PeftModelForSeq2SeqLM` |
| `"SEQ_CLS"` | 문장 전체를 분류한다 | `PeftModelForSequenceClassification` |
| `"TOKEN_CLS"` | 토큰마다 분류한다 (개체명 인식 등) | `PeftModelForTokenClassification` |
| `"QUESTION_ANS"` | 지문 안에서 답의 위치를 찾는다 | `PeftModelForQuestionAnswering` |
| `"FEATURE_EXTRACTION"` | 임베딩 벡터를 뽑는다 | `PeftModelForFeatureExtraction` |
| 주지 않음 | | `PeftModel` (공통 기본 클래스) |

CAUSAL은 "인과적", 즉 앞에서 뒤로만 본다는 뜻이고 LM은 language model이다. 4단계에서 본 "다음 토큰의 점수를 내는 모델"이 causal LM이다. `AutoModelForCausalLM`으로 읽은 모델이므로 `"CAUSAL_LM"`을 준다.

포장 클래스는 모델을 겹겹이 싼 것이다. 스크립트 B 파트가 `q_proj`를 꺼낼 때 쓰는 경로가 그 구조다.

```
model                          PeftModelForCausalLM   <- task_type이 정한 포장
  .base_model                  LoraModel              <- LoRA를 붙이고 관리하는 층
    .model                     Qwen3ForCausalLM       <- 원래 모델
      .model.layers[0].self_attn.q_proj
```

**LoRA + `"CAUSAL_LM"`에서 실제로 달라지는 것은 거의 없다.** `PeftModelForCausalLM`은 `input_ids`, `attention_mask`, `labels` 같은 인자를 받아 원래 모델에 그대로 넘기고, `generate()`도 원래 모델의 것을 부른다. `task_type`을 빼도 LoRA 학습은 같은 결과가 나온다. 그래도 적는 이유는

- `adapter_config.json`에 `"task_type": "CAUSAL_LM"`으로 저장되어, 어댑터를 불러오는 쪽이 어떤 종류의 모델에 붙일 어댑터인지 알 수 있다.
- 포장 클래스가 작업에 맞는 `forward`/`generate` 인자를 갖추고 있어 Transformers의 다른 도구와 맞물린다.

**값이 실제로 중요한 경우.**

- `"SEQ_CLS"`, `"TOKEN_CLS"`: 분류 모델은 사전학습 모델 위에 **새로 만든 분류 층**이 붙어 있다. 이 층은 난수로 시작하므로 얼려 두면 안 된다. 이 `task_type`을 주면 PEFT가 분류 층(`classifier`, `score`)을 학습·저장 대상에 자동으로 넣는다. 빼먹으면 분류 층이 난수인 채로 얼어 학습이 되지 않는다.
- LoRA가 아닌 기법(prompt tuning, prefix tuning): 입력 앞에 학습되는 가짜 토큰을 끼워 넣는 방식이라, 포장 클래스가 입력과 `attention_mask`, `labels`를 직접 고쳐야 한다. 고치는 방법이 작업마다 달라서 `task_type`이 필수다.

**이 프로젝트는 Y/N을 고르는 분류인데 왜 `"SEQ_CLS"`가 아닌가.** 작업의 성격이 아니라 **모델을 쓰는 방식**으로 정하기 때문이다. 이 프로젝트는 분류 층을 새로 붙이지 않고, 원래 모델의 `lm_head`가 내는 다음 토큰 점수에서 ` Y`와 ` N`을 비교한다(4단계). 모델 입장에서는 다음 토큰 예측을 하고 있으므로 `"CAUSAL_LM"`이다. `"SEQ_CLS"`는 `AutoModelForSequenceClassification`으로 읽어 분류 층을 새로 단 모델에 쓴다.

PEFT가 하는 계산은 손으로 만든 `LoRALinear`와 같다. 스크립트의 A 파트와 B 파트가 둘 다 "학습 전 출력이 원래와 같은가: True"를 출력하는 것이 그 확인이다.

### r (rank)
보정 경로의 "폭". `A x`의 결과가 숫자 r개다. 입력(1,024개)이 `A`를 지나며 r개로 줄고, `B`가 그것을 출력 크기(2,048개)로 다시 펼친다.

```
x [1024]  ──A──>  [r]  ──B──>  [2048]
```

보정에 쓰이는 정보는 전부 가운데의 r개짜리 통로를 지나야 한다. r은 이 통로의 폭이고, 위에서 본 "읽고 미는 규칙"의 개수다.

**파라미터 수가 r에 비례하는 이유.** `A`가 `r × 입력`, `B`가 `출력 × r`이라 합이 `r × (입력 + 출력)`이다.

- 모듈 하나: `q_proj`(1024 → 2048)에 r 16이면 `16 × (1024 + 2048) = 49,152`. W(2,097,152)의 2.3%.
- 모델 전체: 층 하나의 일곱 모듈에서 `(입력 + 출력)`을 다 더하면 22,528이고(아래 표), 28층이라 r 1당 630,784개다. r 4 → 2.5M, 16 → 10.1M, 64 → 40.4M.

**어떻게 정하나.** 계산으로 나오는 값이 아니라 실험으로 고르는 설정값이다.

- 범위: r이 커질수록 제한이 풀리지만, `r × (입력 + 출력)`이 `입력 × 출력`을 넘으면 W보다 파라미터가 많아져 LoRA를 쓰는 의미가 없다. 1024 → 2048 모듈에서는 r 약 683이 그 지점이다.
- 시작점: 8~16에서 시작하는 경우가 많다.
- 고르는 방법: r을 몇 가지(예: 4, 16, 64)로 바꿔 학습하고 **val 점수**를 비교한다. r을 키워도 val이 오르지 않으면 작은 쪽으로 충분하다. train loss는 내려가는데 val이 나빠지면 과적합이니 r을 줄이거나 dropout을 넣는다. 8단계에서 직접 잰다.
- r을 바꾸면 alpha도 같이 바꾼다(아래).

r의 크기에 따른 경향은

- 작으면: 바꿀 수 있는 것이 적다 → 과적합 덜하고 빠르다. 간단한 작업(형식·분류)이면 8~16으로 충분한 경우가 많다.
- 크면: 표현력 ↑, 메모리·어댑터 크기 ↑. 데이터가 적으면 이득이 거의 없다.
- 실전 설정의 16은 "Y/N 판단"이 어려운 작업은 아니라고 보고 고른 보수적인 값.

### alpha와 scale = alpha / r
보정에 곱하는 배율. `alpha = 2r`(scale 2)이 관례이고 실전 설정도 그렇다(16/32). r을 바꾸면 alpha도 같은 비율로 바꿔야 "보정의 세기"가 유지된다.
scale을 키우는 것은 lr을 키우는 것과 비슷한 효과(보정이 출력에 더 크게 반영).

### target_modules
모델 안에는 `y = W x` 계산을 하는 부품이 수백 개 있다. `target_modules`는 그중 **어느 부품에 LoRA를 붙일지** 고르는 설정이다.

**1. 부품(nn.Linear)이란.** 지금까지 LoRA를 `y = W x` 하나에 붙이는 것으로 설명했다. PyTorch에서는 이 `y = W x` 계산을 하는 부품을 `nn.Linear`라고 부른다. nn.Linear 하나가 가중치 행렬 `W` 하나를 갖고 있다. (PyTorch에서는 이런 부품을 "모듈"이라고 한다. `target_modules`의 modules가 이것이다.)

**2. 모델에 이런 부품이 몇 개 있나.** Qwen3-0.6B는 똑같은 구조의 **층**을 28개 쌓은 모델이다. 층 하나에 nn.Linear가 7개 들어 있다. 그래서 7 × 28 = 196개이고, `W`도 196개다.

**3. 부품마다 이름이 있다.** 이름은 그 부품이 모델 안 어디에 있는지를 적은 것으로, 폴더 경로처럼 읽는다.

```
model.layers.0.self_attn.q_proj
  모델  >  층들  >  0번 층  >  attention  >  q_proj
```

196개의 이름을 늘어놓으면 이렇다. 층마다 같은 7개가 반복된다.

```
model.layers.0.self_attn.q_proj       ← 0번 층
model.layers.0.self_attn.k_proj
model.layers.0.self_attn.v_proj
model.layers.0.self_attn.o_proj
model.layers.0.mlp.gate_proj
model.layers.0.mlp.up_proj
model.layers.0.mlp.down_proj
model.layers.1.self_attn.q_proj       ← 1번 층 (같은 7개)
...
model.layers.27.mlp.down_proj         ← 27번 층
```

층 번호만 다르고 이름의 **마지막 부분**(`q_proj` 등)은 같다.

**4. `target_modules`에는 그 마지막 부분을 쓴다.** `target_modules=["q_proj"]`라고 쓰면 PEFT는 이름이 `.q_proj`로 끝나는 부품을 전부 고른다. 28개 층에 하나씩 있으므로 28개다. 맨 위에서 "어느 부품"을 고른다고 한 것이 이 방식이다.

| 설정 | LoRA가 붙는 부품 | 개수 | 학습 파라미터 (r 16) |
|---|---|---|---|
| `["q_proj"]` | 모든 층의 q_proj | 28 | 1.4M |
| `["q_proj", "v_proj"]` | 모든 층의 q_proj, v_proj | 56 | 2.3M |
| 일곱 이름 전부 | 모든 층의 모든 nn.Linear | 196 | 10.1M |

**5. "붙인다"는 것.** 고른 부품마다 그 `W` 옆에 `A`, `B`가 한 쌍씩 새로 생긴다. 196개 부품에 붙이면 `A`, `B`도 196쌍이고, 쌍마다 따로 학습되어 서로 다른 값이 된다. 스크립트의 B 파트에서 `q_proj`의 타입이 바뀌고 안에 `lora_A`, `lora_B`가 생긴 것이 이것이다.

**일곱 부품은 각각 무엇인가.** 이름 뒤의 `proj`는 projection의 줄임으로, "`W x`로 벡터를 다른 벡터로 바꾸는 부품"이라는 뜻일 뿐이다. 구분되는 것은 앞부분(q, k, v, o, gate, up, down)이다.

먼저 층 하나가 하는 일을 본다. 모델 안에서 토큰 하나는 숫자 1,024개짜리 벡터로 표현된다. 층은 이 벡터를 받아 조금 고친 뒤 다음 층에 넘긴다. 고치는 일은 두 묶음이 차례로 한다.

1. **attention**: 다른 토큰들을 둘러보고 필요한 정보를 가져온다.
2. **MLP**: 가져온 정보로 자기 벡터를 가공한다. 다른 토큰은 보지 않는다.

이 프로젝트의 입력으로 예를 들면, `[2] 급여 명세서 출력`의 답을 정하려면 앞에 있는 `질문: 재고 수량이 안 맞아요`를 봐야 한다. 앞의 토큰에서 정보를 끌어오는 일이 attention이고, 끌어온 정보로 "재고 질문에 급여 문서는 관련이 없다"는 쪽으로 벡터를 가공하는 일이 MLP다. 실제 모델이 정확히 이렇게 나눠 일한다는 뜻은 아니고, 두 묶음의 역할 차이를 보이기 위한 예다.

"벡터를 가공한다"를 풀어 보면 이렇다. 토큰 자리마다 있는 숫자 1,024개는 **모델이 그 자리에서 지금까지 파악한 내용**을 담는다. 마지막 층을 지난 벡터가 `lm_head`로 들어가 다음 토큰의 점수가 되므로(4단계), 답이 나올 자리의 벡터가 어떤 숫자들이냐에 따라 ` Y`와 ` N` 중 어느 쪽 점수가 높을지가 정해진다. `[2]` 바로 뒤, 즉 Y/N을 예측하는 자리의 벡터를 따라가 보면

| 시점 | 그 자리의 벡터에 담긴 것 |
|---|---|
| 층에 들어올 때 | "여기는 `[2]` 다음 자리다" 정도. 질문이나 문서 내용은 아직 모른다 |
| attention 뒤 | 다른 자리에서 가져온 "질문은 재고에 관한 것", "2번 문서는 급여에 관한 것"이 더해져 있다 |
| MLP 뒤 | 두 정보를 조합한 새 내용 "둘의 주제가 다르다"가 더해져 있다 |

attention은 다른 자리의 내용을 **가져와 섞기만** 한다. 재고 정보와 급여 정보가 한 벡터 안에 나란히 놓일 뿐, "그래서 둘이 관련이 있는가"라는 결론은 아직 없다. 그 결론을 계산해 벡터에 써넣는 것이 MLP다. 아래에 나오는 세 부품으로 보면

- `up_proj`와 `gate_proj`가 벡터를 3,072칸으로 펼친다. 칸 하나하나가 "이런 조합이 있는가"를 검사하는 자리다. 예를 들어 어떤 칸은 "재고 정보와 급여 정보가 같이 있을 때"만 문이 열린다.
- `down_proj`가 열린 칸들을 보고 벡터의 숫자들을 고친다. 위 칸이 열렸다면 "주제가 다르다"에 해당하는 방향으로 벡터를 민다.

"관련이 없다는 쪽으로"는 이렇게 벡터의 숫자들이 **나중에 ` N`의 점수가 높아지는 방향**으로 바뀐다는 뜻이다. 층 하나가 이 일을 다 하는 것은 아니고, 28개 층이 조금씩 가져오고 가공하기를 반복한 결과가 마지막 벡터다. 칸 하나가 사람이 읽을 수 있는 뜻을 갖는다는 보장도 없다. LoRA를 MLP의 세 부품에 붙이면 이 "어떤 조합을 검사하고, 그때 벡터를 어떻게 고칠지"가 바뀐다.

일곱 부품 중 넷은 attention 안에서, 셋은 MLP 안에서 쓰인다.

```
층 입력 (토큰마다 숫자 1,024개)
  ├─ attention:  q_proj, k_proj, v_proj  →  점수 매기기, 정보 가져오기  →  o_proj
  └─ MLP:        up_proj, gate_proj  →  칸마다 곱하기  →  down_proj
층 출력 (토큰마다 숫자 1,024개)
```

**attention의 네 부품.** 도서관에서 자료를 찾는 일에 비유할 수 있다. 정보를 찾는 토큰이 "찾는 사람"이고, 나머지 토큰들이 "책"이다.

| 이름 | 비유 | 입력 → 출력 | 하는 일 |
|---|---|---|---|
| `q_proj` (query) | 검색어 | 1024 → 2048 | 찾는 토큰의 벡터로 "내가 찾는 것"을 나타내는 벡터를 만든다 |
| `k_proj` (key) | 책 표지의 색인 | 1024 → 1024 | 각 토큰의 벡터로 "나는 이런 정보를 갖고 있다"를 나타내는 벡터를 만든다 |
| `v_proj` (value) | 책의 본문 | 1024 → 1024 | 각 토큰의 벡터로 실제로 넘겨줄 내용 벡터를 만든다 |
| `o_proj` (output) | 가져온 자료 정리 | 2048 → 1024 | 가져온 내용을 합쳐 원래 크기(1,024)로 되돌린다 |

순서대로 보면

1. 찾는 토큰이 `q_proj`로 검색어를 만든다.
2. 모든 토큰이 `k_proj`로 색인을, `v_proj`로 본문을 만든다.
3. 검색어를 각 토큰의 색인과 비교해 점수를 매긴다. 6단계에서 본 `길이 × 길이` 점수표가 이것이다.
4. 점수가 높은 토큰의 본문은 많이, 낮은 토큰의 본문은 적게 섞어서 가져온다.
5. `o_proj`가 가져온 것을 정리하고, 그 결과가 자기 벡터에 더해진다.

네 부품 모두 "토큰의 벡터에 `W`를 곱해 다른 용도의 벡터를 만드는" `W x` 계산이다. 그래서 각각 자기 `W`가 있고, LoRA를 붙일 수 있다. q와 k에 붙인 LoRA는 **어디를 볼지**를 바꾸고, v와 o에 붙인 LoRA는 **무엇을 가져올지**를 바꾼다.

q만 출력이 2,048인 것은 세부 사항이다. attention은 위 과정을 여러 벌(헤드) 동시에 돌리는데, 검색어 쪽은 16벌 × 128 = 2,048이고 색인과 본문 쪽은 8벌 × 128 = 1,024다. 색인·본문 한 벌을 검색어 두 벌이 같이 써서 k와 v의 크기를 절반으로 줄인 구조다(grouped-query attention).

**MLP의 세 부품.** MLP는 다른 토큰을 보지 않고 **토큰 하나의 벡터를 가공하는** 묶음이다. attention이 가져온 정보를 바탕으로 새 특징을 계산한다.

| 이름 | 뜻 | 입력 → 출력 | 하는 일 |
|---|---|---|---|
| `up_proj` | 넓히기 | 1024 → 3072 | 벡터를 3배 넓게 펼친다. 가공할 재료다 |
| `gate_proj` | 문(gate) | 1024 → 3072 | 같은 벡터로 3,072칸 각각을 얼마나 통과시킬지 정한다 |
| `down_proj` | 줄이기 | 3072 → 1024 | 통과한 결과를 원래 크기로 줄인다 |

순서대로 보면

1. `up_proj`가 벡터를 3,072칸으로 펼친다.
2. `gate_proj`가 같은 벡터로 3,072칸짜리 "문" 값을 만든다.
3. 둘을 칸마다 곱한다. 문이 닫힌 칸(값이 0에 가까운 칸)은 내용이 지워지고 열린 칸만 남는다.
4. `down_proj`가 남은 것을 1,024칸으로 줄이고, 그 결과가 자기 벡터에 더해진다.

**모듈별 LoRA 크기 (r 16).**

| 모듈 | 입력 + 출력 | LoRA 파라미터 | W 대비 |
|---|---|---|---|
| `q_proj`, `o_proj` | 3,072 | 49,152 | 2.3% |
| `k_proj`, `v_proj` | 2,048 | 32,768 | 3.1% |
| `gate_proj`, `up_proj`, `down_proj` | 4,096 | 65,536 | 2.1% |
| 층 하나 합계 | 22,528 | 360,448 | |

28층이면 `360,448 × 28 = 10,092,544`다. 스크립트를 실행하면 B 파트가 `trainable params: 10,092,544`를 출력하는데(아래 "실행하고 볼 것"), 손으로 계산한 이 값과 정확히 같다. 여기서 B는 LoRA의 행렬 `B`가 아니라 스크립트의 두 번째 파트 이름이다. attention 네 모듈이 45%, MLP 세 모듈이 55%를 차지한다. q와 v에만 붙이면 `(49,152 + 32,768) × 28 = 2,293,760`이다.

**붙지 않는 것.** 목록에 이름이 없는 모듈에는 붙지 않는다. 임베딩(`embed_tokens`), 마지막 변환(`lm_head`), 정규화 층들은 원래 값 그대로 고정된다.

**어디에 붙일까.**
- 원 논문은 q, v에만 붙였지만 요즘은 전부 붙이는 쪽이 보통 더 좋다(같은 파라미터 예산이면 r을 줄이고 모듈을 늘리는 편이 낫다는 보고가 많다).
- Qwen3.6-35B에는 이 외에 Gated DeltaNet 층의 `in_proj_qkv, in_proj_z, out_proj`와 공유 expert가 있고, 256개 expert는 nn.Linear가 아니라 3차원 파라미터라 `target_parameters`(`--lora-experts`)로만 붙는다.

### dropout
LoRA 경로에 넣는 dropout. 데이터가 적으면 0.05~0.1을 쓰기도 한다. 실전 설정은 0 - expert `target_parameters`가 dropout 0을 요구하고, 2,950문항 × 1 epoch라 과적합 여지가 적다.

**dropout이 들어가는 자리.** nn.Linear에 붙인 보통의 LoRA는 이렇게 계산한다.

```
y = W x  +  B (A (dropout(x))) · s
```

dropout은 학습 중에 `x`의 일부 칸을 무작위로 0으로 만든다. 보정 경로로 들어가는 `x`에만 적용되고 `W x` 쪽은 그대로다. 매번 다른 칸이 지워지므로 `A`, `B`가 특정 칸에만 기대어 훈련 데이터를 외우기 어려워진다.

**"expert `target_parameters`가 dropout 0을 요구한다"는 말.** 세 가지를 차례로 알아야 한다.

1. **expert**: Qwen3.6-35B의 MLP는 하나가 아니라 층마다 작은 MLP 256개로 되어 있고(이것들이 expert), 토큰마다 그중 일부만 골라 쓴다. 256개의 가중치가 nn.Linear 256개로 나뉘어 있지 않고, `(256, …)` 모양의 3차원 파라미터 하나에 묶여 저장되어 있다.
2. **`target_parameters`**: nn.Linear가 아니므로 `target_modules`로는 고를 수 없다. 대신 파라미터를 이름으로 직접 지정하는 PEFT 설정이 `target_parameters`다. 실전 코드에서는 `--lora-experts`를 켰을 때만 쓴다.
3. **왜 dropout을 못 쓰나**: 두 방식은 LoRA를 적용하는 자리가 다르다.

| | nn.Linear에 붙일 때 (`target_modules`) | 파라미터에 붙일 때 (`target_parameters`) |
|---|---|---|
| PEFT가 하는 일 | 부품의 입력 `x`를 받아 보정 `B(A x)`를 따로 계산해 더한다 | 모델이 파라미터를 읽을 때 `W` 대신 `W + s·B·A`를 돌려준다 |
| PEFT가 `x`를 보나 | 본다 | 보지 못한다 |
| dropout | `x`에 걸 수 있다 | 걸 `x`가 없다 |

3차원 파라미터는 모델 코드가 직접 꺼내 계산에 쓰기 때문에, PEFT가 그 계산의 입력 `x`를 가로챌 수 없다. 할 수 있는 일은 꺼내 가는 값 자체를 `W + s·B·A`로 바꿔 주는 것뿐이다. dropout은 `x`에 거는 것인데 이 방식에는 `x`가 등장하지 않으므로 넣을 자리가 없다. 그래서 PEFT는 이 경우 `lora_dropout`이 0이 아니면 에러를 내고 멈춘다(`does not work with lora_dropout != 0`).

`lora_dropout`은 `LoraConfig` 하나에 값이 하나라, expert에 LoRA를 붙이려면 다른 부품의 dropout도 같이 0이어야 한다. 실전 설정을 0으로 둔 것은 `--lora-experts`를 켜도 같은 설정으로 돌아가게 하기 위해서다.

### QLoRA (Quantized LoRA) - 이 프로젝트에서는 쓰지 않는다
LoRA에 **기반 모델의 4비트 양자화**를 더한 방법이다. LoRA가 줄이는 것은 학습용 메모리(기울기 + Adam 상태)이고, 얼린 가중치 `W`는 여전히 통째로 메모리에 올라간다(35B면 72GB). QLoRA는 이 `W`를 줄인다. 이 프로젝트는 96GB GPU에 bf16 가중치가 들어가므로 쓰지 않는다. GPU가 더 작을 때의 선택지다.

**양자화란.** 숫자를 더 적은 비트로 거칠게 저장하는 것이다. bf16은 값 하나에 16비트를 쓴다. 4비트로는 16가지 값만 구분할 수 있으므로, 미리 정한 눈금 16개 중 가장 가까운 것의 **번호(0~15)** 만 저장한다. −1부터 1까지 균등하게 눈금 16개를 둔 예로 보면

| 원래 값 | 가장 가까운 눈금 | 저장하는 번호 |
|---|---|---|
| 0.12 | 0.067 | 8 |
| 0.03 | 0.067 | 8 |
| −0.53 | −0.467 | 4 |
| 0.91 | 0.867 | 14 |

0.12와 0.03이 같은 눈금으로 뭉개진다. 이만큼 정보를 잃는 대신 크기가 4분의 1이 된다.

| 저장 방식 | 값 하나 | 0.6B | 35B |
|---|---|---|---|
| bf16 | 2바이트 | 1.2GB | 72GB |
| 4비트 | 0.5바이트 | 약 0.3GB | 약 18GB |

실제로는 양자화하지 않는 부분과 눈금 정보가 더해져 이보다 조금 크다. 양자화 대상은 nn.Linear뿐이라, Qwen3.6-35B의 expert처럼 nn.Linear가 아닌 파라미터는 빠진다. 그런 모델에서는 절감 폭이 위 표보다 작다.

**왜 LoRA와 잘 맞나.** 4비트로 저장된 값은 눈금 16개 중 하나라서, 기울기로 조금씩 움직이는 학습을 할 수 없다. 그런데 LoRA는 `W`를 읽기만 하고 고치지 않는다. 학습은 `A`, `B`가 맡고, 이 둘은 양자화하지 않고 원래 정밀도로 둔다.

```
y  =  W x                         +  B (A x) · s
      4비트로 저장, 계산 직전에       원래 정밀도, 학습한다
      bf16으로 풀어 쓴다. 고정
```

`W`가 거칠어져 생긴 오차도 `A`, `B`가 학습하면서 함께 메운다. QLoRA 논문은 이렇게 학습하면 16비트로 파인튜닝한 것과 비슷한 성능이 나온다고 보고했다.

**논문이 더한 세 가지.**
- **NF4(4-bit NormalFloat)**: 사전학습 가중치는 0 근처에 몰린 종 모양 분포다. 눈금을 균등하게 두지 않고 값이 몰린 곳에 촘촘히 둔다. 같은 16개 눈금으로 오차가 작아진다.
- **이중 양자화(double quantization)**: 가중치를 작은 묶음으로 나눠 묶음마다 배율 상수를 따로 저장하는데, 이 상수들도 한 번 더 양자화해 조금 더 줄인다.
- **paged optimizer**: GPU 메모리가 순간적으로 모자랄 때 일부를 CPU 메모리로 넘겨 학습이 죽지 않게 한다.

**대가.**
- 속도: 계산할 때마다 4비트를 풀어야 해서 bf16 LoRA보다 느리다.
- 정밀도: 학습 내내 `W`가 원래 값과 조금 다른 상태다.
- 서비스: 어댑터는 "4비트로 뭉개진 `W`"에 맞춰 학습된다. 서비스에서 원래 정밀도의 `W`에 붙이면 학습 때와 조금 다른 모델 위에서 돌게 된다.

**코드로는.** 모델을 읽을 때 양자화 설정을 주고, LoRA를 붙이기 전에 준비 함수를 한 번 부른다. `bitsandbytes` 패키지가 필요하다(이 프로젝트 환경에는 없다).

```python
from transformers import BitsAndBytesConfig
from peft import prepare_model_for_kbit_training

bnb = BitsAndBytesConfig(load_in_4bit=True,                       # 4비트로 저장
                         bnb_4bit_quant_type="nf4",               # NF4 눈금
                         bnb_4bit_use_double_quant=True,          # 이중 양자화
                         bnb_4bit_compute_dtype=torch.bfloat16)   # 계산은 bf16으로 풀어서
model = AutoModelForCausalLM.from_pretrained(name, quantization_config=bnb, device_map=device)
model = prepare_model_for_kbit_training(model)   # 전부 얼리고, gradient checkpointing을 켠다
model = get_peft_model(model, lora)              # 여기부터는 LoRA와 같다
```

**메모리를 줄이는 기법 정리.** 네 가지가 각각 다른 것을 줄인다.

| 기법 | 줄이는 것 | 어디서 |
|---|---|---|
| `logits_to_keep` | logits | 6단계 |
| gradient checkpointing | 활성값 | 6단계 |
| LoRA | 기울기 + Adam 상태 | 7단계 |
| QLoRA의 4비트 양자화 | 얼린 가중치 | 쓰지 않음 |

- B: 층 하나의 Linear 목록. `trainable params: 10,092,544 || all params: 606,142,464 || trainable%: 1.67`. 감싼 뒤 `q_proj`가 PEFT의 `Linear`(안에 lora_A, lora_B)로 바뀜. 출력 동일.

## 실전 코드에서는
```python
lora = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.0, task_type="CAUSAL_LM",
                  target_modules=[...], target_parameters=... if args.lora_experts else None)
model = get_peft_model(model, lora)                      # B
model.print_trainable_parameters()                       # B
params = [p for p in model.parameters() if p.requires_grad]   # A·B만 optimizer에 (얼린 W는 제외)
...
model.save_pretrained(args.out)                          # C: 어댑터만 저장
```
`task_type="CAUSAL_LM"`: PEFT에게 "다음 토큰 예측 모델"이라고 알려 준다. LoRA의 계산은 바꾸지 않고, 감싸는 클래스와 저장되는 설정만 정한다(위 "`task_type`은 무엇인가").
